# 第六轮讨论：编译基线、最小协议与验收

以 v1_decisions.md 的已确认要求为前提。以下环境版本、协议及验收细节属于建议，尚未全部定案。

## 当前开发环境（只读检查）
- x86_64，Ubuntu 24.04.1 LTS。
- PATH 可找到 gcc、g++、cmake、pkg-config；可找到 Windows Docker Desktop 附带的 docker 命令，但未验证服务可用。
- PATH 未找到 ninja、meson、podman、aarch64-linux-gnu-g++。
- pkg-config 列出 libmlx5 与 libibverbs，未列出 DOCA 包；这不证明任何路径下都不存在 SDK。
- 未安装、构建、拉取镜像或运行容器。

## 编译基线为何要固定
需要同时确定 SDK 头文件/库版本、目标系统用户态库、处理器架构和构建工具。宿主开发系统不必等同于目标系统，但 AArch64 二进制必须使用目标架构库和兼容的运行时依赖。BFB 是未来设备的系统/固件软件包；不能把“编译通过”视作已验证与未知 BFB 的运行兼容性。

用户说明 CloudLab 申请镜像为 UBUNTU24-64-STD，Host 目标按 Ubuntu 24.04 x86_64 规划。SDK 候选仍为 DOCA 2.9.4 LTS 更新。DPU 为 AArch64，目标用户态必须单独按实际 BFB 确定；2.9.4 默认 BFB 的 Ubuntu 22.04 只是 DPU 候选，不要求 Host 改为 22.04。项目建议 C++17 + CMake。SDK 精确包版本、镜像摘要和编译器版本在环境准备时核实固定。

官方 2.9.4 General Support 列出 BF2、Host/Arm SDK 2.9.4、BSP 4.9.4，BFB 默认 Ubuntu 22.04；Host 支持表同时包含 Ubuntu 24.04 x86，列出的内核为 6.8.0-31-generic。因此 Ubuntu 24.04 本身不排除该 SDK 候选，但 CloudLab 镜像的实际内核、驱动及 DPU BFB 尚未检查，不能仅凭镜像名宣称整套运行兼容。2.9.4 是 2.9.0 的 LTS 更新，并非唯一可选或当前最新版。

## 构建目标
1. 本机软件构建：完整搜索与模拟交接使用同一搜索核心和语义；可运行验证，但不冒充真实 DMA。
2. Host SDK 构建：面向 Ubuntu 24.04，使用真实 x86_64 DOCA 头文件和库编译链接 Host 程序。
3. DPU SDK 构建：使用真实 AArch64 DOCA 头文件和库编译链接 SoC 程序，包含 DMA 实现；核对 ELF 架构和动态依赖。

DPU 构建优先考虑固定容器中的交叉工具链 + 目标根文件系统/SDK 库（sysroot）。如果该版本的交叉依赖准备困难，再采用 QEMU 下的 Arm 用户态开发容器。QEMU 可帮助运行编译器及纯软件程序，不意味着模拟 BlueField DMA 硬件。具体镜像和工具链可获取性尚待环境准备阶段核实。

先编译官方同版本 DMA 示例/最小 SDK 链接检查，再编译项目，以分离环境问题与项目问题。不能用假 DOCA 头文件或软件后端代替真实 SDK 编译验收。

## 最小协议的职责
协议规定双方何时可以使用哪些数据、如何识别任务以及何时可以回收资源。用户已确定 v1 采用消息通道，按此前 DOCA Comch 方案规划。v1 一个在途查询，但跨多次查询必须能区分代次，避免误用旧结果。

建议最少三组控制语义：
- 初始化/就绪：协议版本、数据集/图/PQ 标识、内存区描述、图步长/最大度数、维度、PQ 布局及 SoC 初始化就绪。
- 提交：查询标识、交接状态的区域/偏移/长度、预测簇/预取数据描述、结果存放约定及必要配置。
- 完成/失败：同一查询标识、状态、结果或结果描述、紧凑 benchmark 统计、资源访问已结束的保证。

SoC 接收任务后并行推进状态读取与预测簇数据预取；底层策略独立配置，v1 都使用 DMA。不需要用单个 backend 全局开关绑定后续三类传输选择。用户已确定结果随完成消息返回，需在初始化时检查 top-k 与基础统计载荷是否适配控制通道容量。

## 初始化与内存导出
v1 单边读取仍需初始化阶段建立 Host 可访问区域和访问描述。
DOCA 2.9.0 官方 DMA Copy 应用展示：Host 导出 mmap 描述，经 Comch 交换，DPU 导入后自行发起 DMA。该例可作 v1 控制/数据分离的参考；项目选择 2.9.4 后仍应按该版本实际头文件/示例核对 API。

用户已选择消息通道，v1 按 DOCA Comch 实现逻辑提交/收割，共享环后置。Host 图数据按簇离线连续存储，搜索用图 ID 直接定位图记录，预取通过簇偏移定位；通过 graph_to_dataset 定位原始向量，具体见 protocol_v1.md。

## 就绪与启动条件
预取已提交、状态已就绪、某节点邻接表已就绪是不同状态。必须保证不读取仍在 DMA 写入的目标区。
“几乎同时到达”是调度与性能目标，不能靠代码固定承诺；需测量状态就绪与所需图数据就绪的间隔、首轮等待和预取完成时间。

用户已选择完整交接状态与所有预测簇数据均就绪后开始扩展，以简化 v1。当前触发节点不保证属于预测区域，随后按普通缺失进行 DMA 补读。

完成事件只能在本次相关数据传输全部结束或安全停止后发布，以允许回收 Host 交接/预取暂存区和 SoC 查询缓冲。查询算完也不能忽略仍在途的预取。

## 错误与超时
可控失败：记录错误，停止推进，处理完在途操作后发布可回收的失败结果。
超时/断连：Host 不能仅凭计时结束就复用可能仍被 DMA 访问的内存。先将会话置为失败，待访问停止或映射安全撤销后清理；具体 SDK 清理步骤后续核对。
v1 建议不自动重试和回退 Host，以免引入重复执行与状态合并。

## 验收建议
A. 输入和布局：定长图保留原 CSR 的有效邻居及顺序，padding 不参与扩展，PQ 与图/向量 ID 对齐；用元数据实际检查最大度，不能只按 R=32 文件名推断。
B. 搜索语义：同平台、同策略和确定性距离实现下，对照完整 Host 搜索，恢复后扩展序列、最终候选/top-k、预算计数、终止原因一致。两条路径都使用同一重排图和图 ID 排序规则；与旧 predict 原始 ID 排序产生的同距差异单独分析。
C. 预取与补读：预测簇确实被读取且查询使用预取数据；强制未命中可正确 DMA 补读；全精度向量走独立重排路径；PQ 不发生逐邻居远程读取。模拟后端可注入不同完成顺序和失败验证就绪/资源规则。
D. 协议：初始化不匹配、未触发、空预测窗口、查询连续提交、旧完成事件、传输失败等行为明确；消息提交失败或资源不足不得伪装提交成功；完成后资源可复用，失败不能伪装空数据继续搜索。
E. 编译：三个构建目标分别报告；真实 SDK 的 DMA 适配器必须实际进入构建和链接，不得仅生成软件后端。
F. 性能：基础插桩可用；无设备阶段不设硬件加速比或“同时到达”数值门槛。真机再验证 BF2 设备能力、实际 DMA 内容、完成顺序与性能；跨架构浮点误差的数值容差另定。
